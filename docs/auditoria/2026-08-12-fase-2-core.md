## 2. Mapa de arquitectura desde el código

### Puntos de entrada

`index.html` → `src/index.tsx` → `src/App.tsx` → `src/components/routing/AppRouter.tsx`.

`index.tsx` arranca asíncrono: hace `fetch('/default-project.json')`, después intenta pisar ese
default con `localStorage['textureAppProject']`, y recién ahí monta `<App>`. Si el fetch falla,
renderiza un mensaje de error y no monta la app.

### Capas

| Capa | Ubicación | Líneas |
|---|---|---|
| Estado global (Zustand, 9 slices) | `src/store/` | 3.824 |
| Utilidades (validación, migración, hot reload, métricas) | `src/utils/` | 4.003 |
| Pipeline gráfico (compositor + workers + trust store) | `src/graphics-pipeline/` | 1.839 |
| Registro y host de renderers | `src/components/renderers/` | 1.888 |
| Controles declarativos | `src/components/declarative/` | 1.662 |
| Secuenciador | `src/components/sequencer/` | 917 |
| Debug | `src/components/debug/` | 811 |
| i18n | `src/i18n/` | 653 |
| Resto de UI (layout, dualscreen, midi, error, routing) | `src/components/` | ~2.800 |

### Flujo de un frame

1. `MainApp` resuelve el renderer activo desde el store (`state.project.globalSettings.renderer`,
   default `'webgl'`) y lo pasa a `GraphicsPipelineHost` vía `PipelineViewportCanvas`
   (`MainApp.tsx:27-44`).
2. `GraphicsPipelineHost` monta un `WebGLCompositor` sobre el `<canvas>` y arranca un
   `requestAnimationFrame` permanente (`GraphicsPipelineHost.tsx:518-542`).
3. Antes de crear ningún worker, corre una fase de validación: `hydrateCommunityTrustStore()`,
   `validateRendererSdkContract()`, descarga del `workerEntry`, checksum y firma
   (`:619-684`). Sólo al terminar pone `isRendererValidated = true`.
4. Con la validación en verde, crea un `RendererWorkerManager` que hace handshake con el worker
   externo y le transfiere un `OffscreenCanvas` (`:439-480`).
5. El worker devuelve `ImageBitmap` por frame; el compositor los sube a la textura de su fuente
   (`A` o `B`) y mezcla con `mixFactor`.
6. Al cambiar de renderer, se crea el segundo worker en la fuente libre y se hace crossfade de
   800 ms; al terminar se descarta el anterior (`:520-535`, `:725-739`).

### Cómo llegan los datos al worker

`GraphicsPipelineHost` se suscribe al store completo y empuja uniforms en **cada** cambio:

```ts
unsubscribeStoreRef.current = useTextureStore.subscribe((state) => {
  syncUniforms(state);
});
```
(`GraphicsPipelineHost.tsx:557-559`)

No hay selector ni comparación: cualquier mutación del store —incluido el log MIDI o el paso del
secuenciador— dispara el empuje de todos los uniforms del renderer activo. Es el eje de la
investigación abierta en `docs/next-steps/pipeline-cadence.md`.

### Registro de renderers

`src/components/renderers/index.ts` mantiene una allowlist hardcodeada de 4 entradas
(`ALLOWED_RENDERERS`, `:147-240`): `webgl`, `diagnostic-fps`, `concentric`, `dvd-screensaver`.
Cada una lleva su `packageManifest` completo copiado a mano, con `source: 'builtin'`.

Ninguna tiene componente React: todas usan `EmptyExternalRenderer = () => null` (`:9`). El
dibujado ocurre íntegramente en el worker externo servido por `core-renderers`.

El segundo registro, `HARDCODED_EXTERNAL_RENDERERS`, es **un array vacío** (`:265`).

## 5. Deuda y riesgos, por impacto

### C1 — El host del pipeline hardcodea cada renderer 🔴

`applyRendererUniforms` (`GraphicsPipelineHost.tsx:233-351`) es una cadena de comparaciones por
id:

```ts
if (rendererId !== 'webgl') {
  if (rendererId === 'diagnostic-fps') { /* 60 líneas */ }
  if (rendererId === 'concentric')     { /* ... */ }
  if (rendererId === 'dvd-screensaver'){ /* ... */ }
  return;
}
// resto: uniforms de webgl
```

Cada renderer nuevo obliga a editar el core, recompilarlo y publicarlo. Eso **contradice
frontalmente** la arquitectura que el resto del sistema construye: allowlist con identidad
canónica, manifests, protocolo de worker versionado, trust store y firma criptográfica — todo
pensado para cargar herramientas de terceros sin tocar el core.

El sistema tiene la puerta blindada y la pared abierta: un tercero no puede publicar un renderer
funcional aunque supere toda la cadena de validación, porque sus uniforms no tienen rama en el
`if`. Es el techo real del marketplace, no la seguridad.

Peor aún, la rama de `diagnostic-fps` **genera datos** en el host (senos, cosenos y un payload
sintético de hasta 64 KB, `:261-297`). Lógica de un renderer viviendo en el core.

### C2 — Cinco tests fallan sin CI que lo note 🔴

5/88 en rojo, con dos causas raíz distintas (§1). No es un descubrimiento nuevo —el `STATUS.md`
de la raíz ya los registraba— pero llevan meses así y nada los bloquea: no hay workflow de
GitHub Actions, y el `npm run lint` que sería el otro gate está roto por `--max-warnings 0`
contra 260 warnings.

El repo tiene los cuatro gates configurados y ninguno puede fallar un merge.

### C3 — La seguridad community es infraestructura sin consumidor 🔴

Ver § 4.3. ~1.100 líneas entre trust store, firma, checksum y tokens, más 15 variables de
entorno, cuya única ejercitación es la suite de tests.

Lo clasifico 🔴 no por riesgo de seguridad —no hay superficie expuesta, justamente porque no
corre— sino por costo de mantenimiento y por lo que revela: se endureció la carga de plugins de
terceros antes de que existiera un tercero, y antes de resolver C1, que es lo que realmente
bloquea a ese tercero. El orden de construcción quedó invertido.

### C4 — 1.923 líneas muertas 🟠

Ver § 4.1. El caso más señalado es `errorRecovery.ts` (630 líneas): un sistema de recuperación
de errores completo que nadie invoca, en una app cuyo `RendererErrorBoundary` sí está bien
cableado en los tres caminos de render (`MainViewport.tsx:32`, `MainApp.tsx:139`,
`SecondaryDisplay.tsx:99`).

`recording.slice.ts` merece mención aparte por estar **vacío**: es un archivo de 0 bytes
commiteado, reservando el nombre de una funcionalidad planeada.

### C5 — El contrato de controles declara más tipos de los que el core implementa 🟠

`@luxsequencer/contracts` declara 10 `ControlType`
(`luxsequencer-contracts/src/declarativeControls.ts:1-11`):

`slider`, `color`, `gradient`, `select`, `toggle`, `vector2d`, `range`, `curve`, `matrix`, `text`.

El core implementa **8**. No hay `curve` ni `matrix`:

- `src/components/declarative/controls/` tiene 8 componentes; falta `CurveControl` y `MatrixControl`.
- El `switch` de `ControlRenderer.tsx:47-105` no tiene `case 'curve'` ni `case 'matrix'`, y
  **no tiene `default`**. Cierra con el comentario `// Add other constraint types as needed`.

Un renderer de terceros que declare un control `curve` **type-checkea sin error** contra el
contrato publicado, y después cae por el `switch` sin constraints y sin ningún aviso. Falla
silenciosa en el borde exacto donde el sistema promete extensibilidad.

Es el mismo patrón que la auditoría de `core-renderers` documentó como R3 (controles declarados
sin implementación), pero un nivel más arriba: acá el que miente es el contrato compartido.

### C6 — Los uniforms se empujan en cada cambio del store 🟠

`useTextureStore.subscribe((state) => syncUniforms(state))` sin selector ni igualdad
(`GraphicsPipelineHost.tsx:557-559`). Cualquier mutación —`midiLog`, `sequencerCurrentStep`,
estado de drawers— reenvía el conjunto completo de uniforms a los workers activos (hasta dos
durante un crossfade).

Ya hay una investigación abierta con una medición hecha en
`docs/next-steps/pipeline-cadence.md`, que descartó una hipótesis sin confirmar otra. Lo dejo
anotado como deuda con su documento vivo, no como hallazgo nuevo.

Mitigación parcial ya presente: la rama de `diagnostic-fps` cachea su config serializada en un
`WeakMap` para no reenviar los cinco uniforms de configuración si no cambiaron (`:281-288`).
Ningún otro renderer tiene esa protección.

### C7 — El compositor voltea todas las fuentes y cada renderer lo compensa por su cuenta 🟠

`WebGLCompositor.ts:228` aplica `gl.pixelStorei(gl.UNPACK_FLIP_Y_WEBGL, 1)` a toda textura
subida, sin importar de dónde venga.

Los workers lo compensan de forma inconsistente:

- `diagnostic-fps.worker.ts:226` — `setTransform(1, 0, 0, -1, 0, canvas.height)`: voltea a mano.
- `dvd-screensaver.worker.ts:128` — `setTransform(1, 0, 0, 1, 0, 0)`: identidad, no compensa. **Se ve invertido.**
- `concentric` — lo esconde por simetría de su dibujo.

La auditoría de `core-renderers` lo registró como R1 y dejó explícitamente la decisión para esta
sesión, porque **el arreglo es de contrato y el contrato lo define el core**: hoy la orientación
del `ImageBitmap` que un worker debe entregar no está escrita en ningún lado. Cada autor la
descubre mirando el resultado en pantalla.

Queda como pregunta abierta (§7, P2), no lo resuelvo acá.

### C8 — El bundle es un único chunk de 520 kB 🟡

Sin `manualChunks` ni `import()` dinámico salvo el de los schemas declarativos
(`index.ts:361`). Vite lo avisa en cada build. No es crítico para una app de escritorio local,
pero sí para el modelo de distribución web que el ecosistema tiene planeado.

### C9 — `LICENSE` está vacío 🟡

Archivo de 0 bytes, `package.json` sin campo `license`, y el README afirmando GPL-3.0
(`README.md:157`). El `STATUS.md` de la raíz ya marca "Licencias abiertas en core y
core-renderers" como PLANEADO y lo remite a los bloqueantes del modelo de distribución, así que
la decisión está tomada como pendiente — lo que sobra es la afirmación del README.

### C10 — Ruido menor 🟡

- `default-project.json` duplicado idéntico en raíz y `public/` (§4.2).
- `logEnvConfig()` es un no-op que igual se llama en el arranque (§4.4).
- Bloque de "Hot Reload Indicator" comentado en `MainApp.tsx:177-181`.
- `import { useRendererHotReload as _useRendererHotReload }` (`MainApp.tsx:24`): el prefijo `_`
  sugiere que no se usa, pero sí se invoca en `:65`. El alias engaña al lector.

## 6. Lo que sí está bien

Vale registrarlo, porque la tabla de drift no da la proporción correcta.

- **El type-check está limpio** sobre 20.419 líneas, con `isolatedModules` y `moduleResolution:
  bundler`. En un repo de este tamaño y con esta cantidad de refactors encima, no es poco.
- **El pipeline gráfico funciona y está bien construido.** Crossfade de 800 ms entre dos workers,
  latest-frame-wins por fuente, health-check con timeout de stalls, feature detection previa,
  `dispose` explícito de todos los recursos en el cleanup del efecto
  (`GraphicsPipelineHost.tsx:578-608`). El cleanup es notablemente cuidadoso: RAF, suscripción al
  store, `ResizeObserver`, dos intervals y los dos workers.
- **`RendererErrorBoundary` está cableado en los tres caminos de render**, incluido el de la
  ventana secundaria. Lo verifiqué específicamente porque sospeché lo contrario al leer
  `MainApp.tsx`, y la sospecha era infundada.
- **`docs/ENVIRONMENT_VARIABLES.md` está prácticamente al día**: 25 variables, todas reales, una
  sin documentar. Es el contraejemplo de que la doc de este repo no está podrida por igual.
- **`docs/next-steps/pipeline-cadence.md` es el modelo a seguir**: línea de estado, fecha de
  verificación, hipótesis marcada como tal, medición ejecutada y un resultado que descarta la
  hipótesis original sin inventar una nueva. Es exactamente lo que el `STATUS-PROTOCOL` busca.
- **La adopción de `@luxsequencer/contracts` es real**, no decorativa: `src/types/*` re-exporta
  los tipos compartidos y los adapta, tal como el README promete (`declarativeControls.ts:1-25`).

## 7. Preguntas abiertas para el autor

**P1 — ¿El marketplace de terceros sigue siendo un objetivo?** Si lo es, C1 (uniforms
hardcodeados por renderer) es el bloqueante real y hay que diseñar un contrato genérico de
uniforms antes de seguir endureciendo la carga. Si no lo es, sobran ~1.100 líneas de trust store,
firma y licencias, más 15 variables de entorno. Las dos respuestas son razonables; lo que no se
sostiene es el estado actual, que paga el costo de ambas y el beneficio de ninguna.

**P2 — ¿Dónde se define la orientación del `ImageBitmap`?** (C7) Tres opciones: que el compositor
deje de voltear y cada worker entregue en orientación de pantalla; que el compositor siga
volteando y se documente como parte del contrato de worker; o que el manifest declare la
